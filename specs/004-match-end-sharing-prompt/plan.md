# Implementation Plan: Asking at the End of a Shared Match, and Sharing Between Matches

**Branch**: `004-match-end-sharing-prompt` | **Date**: 2026-11-06 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/004-match-end-sharing-prompt/spec.md`

## Summary

Sharing already lasts across matches: when a match ends, every device keeps its role and its
links. Two things follow:

- the host's next match lands on any waiting guest, in place of the result, with nothing to
  say so (R-1, R-2);
- whether it lands promptly depends on which of three delivery paths reaches that guest
  first, which is the "sometimes".

Reading the code also found three gaps the spec cannot be met without:

- **Stop sharing between matches never reaches the guests.** The stop notice names the
  host's empty log, which no guest holds (R-3, a defect today).
- **Hosting refuses to start with no match on**, on the phone and from the watch (R-4).
- **A join with no match on never completes.** The guest stays "joining" until a match
  arrives, so it cannot show whose sharing it is on, or leave it (R-5).

The approach:

- **One between-matches state in RekkertCore.** `BetweenMatches` holds:
  - the end-of-match question still open;
  - the new-match notice still open;
  - since when nothing has been on.

  `MatchStore` raises, closes and persists it where the events happen. The views only render
  it (D-1, D-2).
- **Ask with popups that leave the result readable.**
  - On the phone: alerts over the result.
  - On the watch: the answers take the place of Done (D-3).

  Either half of a pair answers for both, over a new pair-only `SharingSignal.answered` (D-4).
  Every answer goes through one engine call, `SharedSession.answer(_:)` on the phone and
  `WatchStandIn.answer(_:)` on the watch, which records it before stopping or leaving. The
  host's Keep reaches guests as `keptSharingAfter` on the access table they already receive
  (D-5).
- **Announce the next match without holding it back.** It is adopted at once, as today, so
  nobody falls out of step. A `NewMatchNotice` blocks scoring on that device until **OK**.
  The phone tells its watch, and posts a notification when neither is in front, reusing
  spec 001's notification path (D-6, D-11).
- **Fix the three gaps, and a fourth.**
  - An empty-log guest accepts the host's Stop on its host link (D-7).
  - Hosting needs no match on (D-8).
  - A join that the host answers with an empty match becomes a waiting guest at once (D-9).
  - A guest that leaves says goodbye, so the host's list drops it rather than showing it out
    of reach (R-13, D-16).
- **Stop a forgotten share.** After 30 minutes with no match on, sharing stops. It is checked
  on a timer and again whenever the app comes back, so an app suspended overnight does not
  resume (D-10).
- **Show sharing where there is no match.**
  - The phone's Home and the watch's start screen get a sharing section: share, code, who is
    on, stop, waiting, and leave (D-8).
  - The start of a match says it will be shared (D-15).
  - The wording moves from "this match" to "sharing" ([contracts/screens.md](contracts/screens.md)).
- **Record it.** Six new sharing-record events (D-12).

Nothing about how a match merges changes. The evidence, decisions and alternatives are in
[research.md](research.md).

## Technical Context

**Language/Version**: Swift 6.2 tools, Swift 6 language mode. Default isolation is
`MainActor` in the apps and in `RekkertSync`; `RekkertCore` is nonisolated.

**Primary Dependencies**: Apple frameworks only, all already in use: SwiftUI, WatchKit,
WatchConnectivity, CoreBluetooth, Network.framework and UserNotifications. Nothing new.

**Storage**:

- `active.json` (`ActiveSession`) gains an optional `betweenMatches`.
- The access table, persisted with it, gains an optional `keptSharingAfter`.
- The Keychain's `KeptCode` is unchanged.
- Sharing-record files are unchanged in format; they gain new event kinds.

**Testing**:

- Swift Testing via `swift test --package-path Packages/RekkertKit`, on macOS with no
  device. `BetweenMatchesTests` goes in `RekkertCoreTests`. The new sync suites run on the
  existing `CourtHarness`, `SimulatedRadio` and `TestClock`, where the 30-minute rule takes
  milliseconds.
- `scripts/verify.sh` is the gate.
- Simulators via `scripts/share.sh --keep` for the screens.
- One real-device evening before release, per [quickstart.md](quickstart.md).

**Target Platform**: iPhone and iPad on iOS 26; Apple Watch on watchOS 10.0 and later; macOS
26 for package tests. Everything used on the watch (`alert`, `confirmationDialog`,
`WKInterfaceDevice.play`) exists on watchOS 10.

**Project Type**: Mobile app with an iPhone app, an embedded watchOS app and a widget
extension, generated by Tuist, over the local Swift package `RekkertKit`.

**Performance Goals** (from the spec):

- Each guest in reach is asked within spec 001's times for a point: 5 s for at least 95%, and
  30 s at most (FR-008, SC-006).
- The other half of a pair closes its question or notice within 10 s of being in touch
  (FR-005, FR-011, FR-013).
- A leaver shows as gone on the host within 15 s (FR-009).
- Sharing stops by 31 min with no match on (SC-008).
- The next match reaches each guest within spec 001's times (FR-014).

**Constraints**:

- No change to the event format, the reducer, draws, schedules or version vectors
  (Principle II).
- Everything on the wire is additive (R-9). Older guests and hosts keep today's behaviour
  and are not disturbed (FR-025).
- iOS suspends a backgrounded host, so the idle rule must also hold for an app that had no
  running time when the 30 minutes passed.
- A phone cannot wake its watch app. A notification is the only way onto the wrist with the
  phone in a bag.

**Scale/Scope**: Spec 001's: a host and up to seven guests, each with a phone and a watch;
evenings of several matches.

The views render alerts and rows, and forward taps. |
| II. Deterministic, convergent state (NON-NEGOTIABLE) | Every device that has seen the same events computes the same state; reconciliation is monotonic | **Pass.** | **Pass.** The host's next match is adopted exactly as today (D-6); the notice gates taps on one device, and changes no match state. Stop between matches (D-7) and the idle stop (D-10) end sharing, not a match: the last match is already filed. A join completing early (D-9) changes the role, which today is set on adopt anyway. The reducer, the events and the merge are untouched, and the convergence suites run unchanged. |
| III. Test the engine, test-first | Device-free tests pin every rule; bug fixes start with a failing test | **Pass.** | **Pass.** R-2's silent arrival, R-3, R-4, R-5 and R-7 each become a test that fails on `9d930e27` and passes after ([quickstart.md](quickstart.md)). `BetweenMatchesTests` pins the pure rules. | IV. verify.sh is the gate | Green means `scripts/verify.sh`; silent runtime invariants are asserted | **Pass.** | **Pass.** No new Info.plist key, entitlement or background mode: local notifications and their category exist already (R-11). The new tests run inside `swift test`, which `verify.sh` calls. If implementation finds a key is needed, its assertion lands in the same change. |
| V. Local-first, private by construction | No servers; nothing leaves the devices at the court unasked | **Pass.** | **Pass.** No new data flow. The host's Keep travels to the guests' devices on links that already carry its name (D-5). The notification is local, on the guest's own phone and watch. The record's new lines hold no names, scores or codes (D-12). Nothing is sent anywhere else. |
